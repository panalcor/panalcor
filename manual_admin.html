Primeros pasos

Acceso al sistema como administrador

El sistema PANALCOR es una aplicación web de página única (SPA) alojada en GitHub Pages y respaldada por Firebase Realtime Database. No requiere instalación: se accede desde cualquier navegador moderno con conexión a internet o a la red WiFi local de fábrica.

URL de acceso

La dirección del portal de inicio es la raíz del sitio GitHub Pages de la organización. Puedes crear un acceso directo en el escritorio del ordenador de oficina o guardarla como marcador en el navegador.

Consejo

Chrome y Edge permiten instalar la web como PWA (aplicación de escritorio). Busca el icono de instalación en la barra de direcciones. Así el sistema abre en ventana propia sin barras del navegador.

Proceso de inicio de sesión

  1. Abre el portal de inicio (panalcor_inicio.html). Si la página detecta que no hay sesión activa, muestra el diálogo de login.
  2. Introduce el usuario admin y tu contraseña. Las credenciales se verifican contra Firebase Authentication.
  3. Tras autenticarse, el sistema carga tu perfil desde Firebase RTDB y redirige al portal de inicio con todos los módulos disponibles.
  4. El sistema solicita permiso para enviar notificaciones del navegador. Concede el permiso: es necesario para las alertas de averías urgentes (ver Capítulo 3).
Importante

Si rechazas el permiso de notificaciones, el sistema no podrá alertarte de averías urgentes ni de preventivos vencidos. Puedes reactivarlo en la configuración del navegador (icono de candado junto a la URL → Notificaciones → Permitir).

Credenciales y seguridad

El perfil admin tiene acceso de lectura y escritura completo a toda la base de datos. Protege la contraseña. Si sospechas que ha sido comprometida, cámbiala desde Firebase Console o desde la pestaña Mecánicos del panel admin (el proceso de reset también funciona para el propio admin).

Perfiles disponibles en el sistema

Perfil Acceso Módulos visibles

mecánico Lectura propia + escritura limitada Sus averías, preventivos asignados, repuestos
encargado Lectura amplia, escritura limitada Panel encargados, turnos, averías (lectura)

Cerrar sesión

Pulsa el botón de avatar/perfil en la esquina superior derecha del portal de inicio y selecciona Cerrar sesión. No dejes la sesión abierta en ordenadores compartidos.

Si el sistema muestra comportamientos inesperados, comprueba primero la versión. Si es antigua, fuerza la recarga con Ctrl + Shift + R (recarga sin caché) para obtener la última versión.

3
Alertas

Notificaciones automáticas del sistema

El sistema comprueba periódicamente el estado de las averías y preventivos y envía notificaciones push al navegador cuando se detectan situaciones que requieren atención. Estas notificaciones solo llegan al perfil administrador.

Tipos de notificación

Situación Condición exacta Cooldown
URGENTE abierta >1h Avería con prioridad "Urgente" cuya hora de apertura lleva más de 60 minutos sin cerrarse 4 horas
Cualquier avería abierta >6h Cualquier avería activa (cualquier prioridad) que lleve más de 6 horas sin resolverse 4 horas
Preventivo vencido Tarea preventiva con fecha plan ya pasada y estado distinto de "completado" 4 horas

El cooldown de 4 horas significa que la misma alerta (misma avería o mismo preventivo) no volverá a notificarse hasta pasadas 4 horas desde la última vez. Esto evita el spam de notificaciones cuando hay una avería que se alarga.

Cómo activar las notificaciones

  1. Al iniciar sesión como admin, el sistema muestra una solicitud de permiso de notificaciones del navegador.
  2. Haz clic en Permitir en el diálogo del navegador.
  3. El sistema registra el permiso y activa el worker de comprobación periódica en segundo plano.
Atención

Las notificaciones solo funcionan mientras la pestaña del sistema está abierta en el navegador (o minimizada). Si cierras el navegador completamente, dejarás de recibir alertas hasta que vuelvas a abrir el sistema. Se recomienda dejar el portal de inicio abierto en una pestaña durante el horario de trabajo.

Reactivar notificaciones si las rechazaste

Si en su momento rechazaste el permiso, el navegador no vuelve a preguntar automáticamente. Para reactivarlo:

  • Chrome / Edge: Haz clic en el icono de candado (o de información) junto a la URL → Notificaciones → Permitir → Recarga la página.
  • Firefox: Menú → Permisos del sitio → Notificaciones → Permitir.
  • Safari (macOS): Preferencias → Sitios web → Notificaciones → selecciona el sitio → Permitir.

Contenido de las notificaciones

Cada notificación muestra el nombre de la máquina afectada, el tipo de alerta y la hora de detección. Al hacer clic en la notificación, el navegador te lleva directamente a la pestaña del sistema donde puedes actuar sobre la avería o preventivo correspondiente.

Qué mide cada KPI

KPIDefiniciónReferencia ideal
Averías abiertas Número de averías con estado "abierta" en este momento. Incluye todas las prioridades. 0 (objetivo); <3 aceptable en planta activa
MTBF medio (Mean Time Between Failures) Tiempo medio entre fallos, calculado como promedio de todas las máquinas en el período seleccionado. Expresado en horas. Cuanto mayor, mejor. Maquinaria crítica A: >200h
MTTR medio (Mean Time To Repair) Tiempo medio de reparación desde apertura hasta cierre de avería. Promedio de todas las máquinas. Cuanto menor, mejor. Objetivo: <4h para críticas A
Disponibilidad media Calculada como MTBF / (MTBF + MTTR) × 100. Promedio ponderado del parque. >97% para parque industrial alimentario
Mockup — Dashboard admin.html (pestaña Dashboard)

Selector de período

En la parte superior del dashboard hay un selector de período que afecta a los cálculos de MTBF, MTTR y disponibilidad. Las opciones son 30 días, 90 días, 6 meses y 1 año. Las averías activas siempre se muestran en tiempo real independientemente del período.

Desglose por tipo y gravedad

Debajo de la tabla de averías activas, el dashboard muestra dos grupos de contadores:

  • Por tipo: Mecánica, Eléctrica, Hidráulica/Neumática, Otros Trabajos. Estos tipos los elige el mecánico al abrir la avería.
  • Por gravedad: Leve, Moderada, Grave. La gravedad se puede editar desde el detalle de la avería.

Auto-refresco

El panel se refresca automáticamente cada 3 minutos consultando Firebase. Si necesitas ver el estado más reciente de inmediato, usa el botón de recarga manual que aparece en la esquina superior derecha del panel o recarga la página con F5.

Tabla de fiabilidad de máquinas

Dentro del Dashboard, debajo de los KPIs globales, encontrarás la tabla de fiabilidad por máquina. Esta tabla desglosa los indicadores MTBF, MTTR y Disponibilidad para cada máquina del parque individualmente.

Columnas de la tabla

ColumnaDescripciónCómo interpretar
Máquina Código y nombre de la máquina Pinchar abre la ficha histórica (historial_maquina.html)
Criticidad A (crítica), B (importante), C (auxiliar) Define la urgencia de intervención y los objetivos de MTBF
Averías (período) Número de averías cerradas en el período seleccionado Permite detectar máquinas problemáticas
MTBF Tiempo medio entre fallos en horas Bajo MTBF = falla frecuentemente. Revisar plan preventivo
MTTR Tiempo medio de reparación en horas Alto MTTR = reparaciones largas. Revisar repuestos disponibles o formación
Disponibilidad MTBF / (MTBF + MTTR) × 100 El objetivo principal. <95% en máquina A es una señal de alerta

Filtros y ordenación

La tabla permite ordenar por cualquier columna pulsando su cabecera. También puedes filtrar por criticidad (A/B/C) usando los chips encima de la tabla. El período de cálculo se hereda del selector global del dashboard (30d/90d/6m/1año).

Cómo usarla en la práctica

Ordena por Disponibilidad ascendente cada mes. Las máquinas al principio de la lista son las que más horas de producción están perdiendo. Estas son las candidatas prioritarias para revisar el plan preventivo o revisar repuestos en stock.

Acceso rápido al historial

Pinchando en el nombre de cualquier máquina en esta tabla accedes directamente a su ficha en historial_maquina.html, con el gráfico de 12 meses y el timeline completo de intervenciones. Ver Capítulo 16 para más detalle.

Panel principal · admin.html → pestaña Averías

Gestión de averías — ver, editar, cerrar

La pestaña Averías de admin.html es el centro de gestión de incidencias correctivas. A diferencia de la vista de los mecánicos, el admin puede ver y editar cualquier avería de cualquier mecánico o máquina.

Filtros disponibles

La tabla de averías tiene los siguientes filtros combinables:

  • Estado: Abiertas / Cerradas / Todas
  • Máquina: Desplegable con todas las máquinas del parque
  • Mecánico: Desplegable con todos los mecánicos
  • Período: Selector de fechas (desde/hasta)
  • Tipo: Mecánica / Eléctrica / Hidráulica / Otros Trabajos
  • Prioridad: Urgente / Importante / Programable

Ver el detalle de una avería

Al pinchar en cualquier fila de la tabla se abre un panel lateral (o modal) con el detalle completo: historial de notas, fechas, mecánico asignado, tipo, fotos adjuntas y tiempo transcurrido.

Editar una avería

Desde el detalle, el admin puede modificar:

  • Mecánico asignado: Reasignar la avería a otro mecánico si el titular no está disponible.
  • Prioridad: Escalar o desescalar la urgencia.
  • Tipo de avería: Corregir si el mecánico lo clasificó incorrectamente.
  • Notas internas del admin: Añadir contexto que no es visible para el mecánico.
  • Fecha de inicio (corrección): Si la avería se abrió con retraso.
Atención

Modificar la fecha de inicio de una avería afecta al cálculo de MTTR y Disponibilidad. Edita solo cuando haya un error real en el registro, no para mejorar artificialmente los indicadores.

Cerrar una avería desde el panel admin

  1. Abre el detalle de la avería desde la tabla.
  2. Revisa que el mecánico haya añadido el diagnóstico y la acción correctiva.
  3. Pulsa el botón Cerrar avería. El sistema registra la hora de cierre, calcula el tiempo de resolución y actualiza los KPIs.
  4. Opcionalmente, añade una nota de cierre del admin (causa raíz confirmada, acción preventiva recomendada).

Averías "Otros Trabajos"

Los mecánicos pueden registrar trabajos no planificados que no son averías en sentido estricto (ajustes, limpieza técnica, trabajos de mejora) bajo el tipo Otros Trabajos. Estos registros aparecen en la tabla de averías filtrados por tipo, y también se incluyen en el informe especial de Alberto (ver Capítulo 17).

Los "Otros Trabajos" no cuentan para el cálculo de MTBF ni MTTR, pero sí suman horas trabajadas al mecánico.

Exportar averías

Desde la pestaña Averías, el botón Exportar genera una hoja Excel con todas las averías del período filtrado actualmente. Útil para informes a dirección o análisis externos.

Panel de mecánicos — contraseñas y carga

La pestaña Mecánicos de admin.html muestra el listado de todos los mecánicos dados de alta en el sistema con información de actividad y carga de trabajo.

Resetear contraseña de un mecánico

  1. Localiza al mecánico en la tabla y pulsa el botón ⋯ Opciones (o icono de llave) al final de su fila.
  2. Selecciona Resetear contraseña.
  3. Introduce la nueva contraseña provisional (mínimo 6 caracteres). El sistema la actualiza en Firebase Authentication.
  4. Comunica la nueva contraseña al mecánico de forma segura. El mecánico puede cambiarla desde su perfil una vez dentro.
Seguridad

No uses contraseñas triviales al hacer el reset (ej: el nombre del mecánico, "1234"). Usa al menos 8 caracteres con letras y números. El sistema no impone complejidad mínima, pero es tu responsabilidad.

Ver carga de trabajo por mecánico

Al pinchar en el nombre de un mecánico se abre un panel de detalle con:

  • Lista de averías activas asignadas (con tiempo transcurrido)
  • Plan preventivo del mes actual (tareas asignadas, completadas, pendientes)
  • Historial de averías cerradas en los últimos 30 días
  • Total de horas trabajadas registradas en el período

Esta vista es idéntica a la que ve el mecánico desde su propio perfil, pero sin restricción de acceso: el admin puede ver todos los mecánicos.

Dar de alta un mecánico nuevo

El alta de nuevos usuarios se hace directamente en Firebase Console (Authentication + RTDB). No hay formulario en la interfaz web para esta operación. Una vez creado en Firebase, el mecánico aparece automáticamente en la lista de este panel.

Gestión de repuestos e inventario

La pestaña Repuestos de admin.html gestiona el inventario de piezas y consumibles del taller. El sistema avisa automáticamente cuando una referencia baja del stock mínimo configurado.

Inventario de repuestos

La tabla de inventario muestra todas las referencias dadas de alta con los siguientes campos:

CampoDescripción
ReferenciaCódigo interno o referencia del fabricante
DescripciónNombre descriptivo del repuesto
Máquina(s)Máquinas en las que se usa este repuesto
Stock actualUnidades en almacén en este momento
Stock mínimoNivel mínimo configurado; si se supera, alerta roja
ProveedorProveedor habitual y referencia de pedido
Última salidaFecha en que se consumió una unidad por última vez

Alertas de stock bajo

Las referencias con stock actual igual o inferior al mínimo aparecen destacadas en rojo en la tabla. También se muestran en un bloque de alertas en la parte superior de la pestaña. El admin debería revisar estas alertas al menos una vez por semana.

Atención

Las alertas de stock bajo no generan pedidos automáticos. El sistema solo avisa; la gestión del pedido al proveedor sigue siendo manual. Una futura versión puede integrar correo de pedido automático.

Pedidos pendientes de mecánicos

Cuando un mecánico registra una avería y marca que ha necesitado un repuesto que no había en stock, queda registrado como pedido pendiente. El admin ve estos pedidos en un panel lateral dentro de la pestaña Repuestos. Desde allí puede:

  • Marcar el pedido como "en curso" (ya se ha contactado al proveedor).
  • Marcar el pedido como "recibido" (actualiza el stock automáticamente).
  • Cancelar el pedido si ya no es necesario.

Dar de alta un repuesto nuevo

  1. Pulsa el botón + Nuevo repuesto en la parte superior de la tabla.
  2. Rellena el formulario: referencia, descripción, máquina asociada, stock inicial, stock mínimo y proveedor.
  3. Pulsa Guardar. El repuesto queda disponible para que los mecánicos lo seleccionen en sus averías.

Editar o dar de baja un repuesto

Usa el botón de opciones (⋯) al final de cada fila para editar cualquier campo o marcar el repuesto como inactivo (no aparece en las listas de mecánicos pero conserva su historial de movimientos).

Plan Preventivo — navegación y estructura

La página preventivo.html es el módulo más complejo del sistema. Gestiona toda la planificación del mantenimiento preventivo: qué se hace, quién lo hace, cuándo y si se ha completado. El acceso es exclusivo del admin; los mecánicos solo ven sus tareas asignadas desde su propia vista.

Las cinco pestañas del módulo

PestañaFunción principal
Plan MensualRejilla de asignación por máquina para el mes seleccionado. Aquí se define quién hace qué.
SeguimientoPorcentaje de cumplimiento por mecánico y carga de trabajo. Vista operativa del mes en curso.
AlarmasLista de tareas vencidas o en riesgo de vencerse. Requiere atención inmediata.
HistorialRegistro histórico de tareas completadas. Permite buscar por máquina, mecánico o período.
CatálogoBiblioteca de tareas preventivas disponibles. El admin puede añadir, editar o desactivar tareas.

Navegación entre meses

En la parte superior de la página hay un selector de mes con botones < (mes anterior) y > (mes siguiente). El mes actual se muestra en el centro. Puedes navegar libremente entre meses pasados (para consultar historial) y futuros (para preparar el plan por adelantado).

Buena práctica

Prepara el plan del mes siguiente durante la última semana del mes en curso. Así los mecánicos lo tienen disponible desde el día 1 y pueden planificarse.

Frecuencias de tareas

Cada tarea del catálogo tiene asignada una frecuencia. Las frecuencias determinan en qué meses aparece la tarea en el plan:

preventivo.html → Plan Mensual

Asignación de mecánicos por máquina

La pestaña Plan Mensual muestra una rejilla donde las filas son las máquinas del parque y las columnas son las tareas preventivas aplicables a cada una. Cada celda tiene dos asignaciones: Titular y Suplente.

Estructura de la rejilla

  • Titular: El mecánico responsable principal de esa tarea en esa máquina ese mes.
  • Suplente: El mecánico que asume la tarea si el titular está ausente.

Ambas asignaciones se configuran pulsando en la celda correspondiente y seleccionando el mecánico en el desplegable. Las asignaciones se guardan en Firebase en tiempo real al seleccionarlas.

Mockup — Plan Mensual (rejilla de asignación)

Función Auto-asignar

El botón Auto-asignar ejecuta un algoritmo de distribución que asigna automáticamente las tareas del mes intentando equilibrar la carga entre los mecánicos disponibles. El algoritmo respeta las especializaciones configuradas en el catálogo (algunas tareas solo pueden ser realizadas por ciertos mecánicos) y las ausencias ya registradas.

Atención

La auto-asignación sobreescribe cualquier asignación manual previa para ese mes. Úsala como punto de partida y luego ajusta manualmente si es necesario. No la uses si ya has publicado el plan y los mecánicos lo están siguiendo.

Navegar por mecánico

El desplegable Ver por mecánico cambia la vista de la rejilla para mostrar solo las tareas asignadas a un mecánico específico. Útil para comprobar si la carga está bien distribuida antes de publicar.

preventivo.html → Plan Mensual

Gestión de ausencias — sustitución automática

El botón 🏥 Ausencias de la pestaña Plan Mensual abre un diálogo para registrar qué mecánicos están ausentes durante ese mes (vacaciones, baja médica, formación externa). Este registro es la base del mecanismo de sustitución automática.

Registrar una ausencia

  1. Pulsa 🏥 Ausencias. Se abre el diálogo de gestión de ausencias del mes visualizado.
  2. Marca el checkbox del mecánico o mecánicos que estarán ausentes ese mes.
  3. Opcionalmente, indica las fechas exactas de ausencia (si no es el mes completo).
  4. Pulsa Guardar.

Qué ocurre cuando hay ausencias

Una vez registrada la ausencia, el sistema actúa de la siguiente forma:

  • Aparece un banner rojo en la parte superior de la pestaña Plan Mensual indicando qué mecánicos están ausentes ese mes.
  • En la rejilla, las celdas donde el mecánico ausente es Titular muestran un indicador visual de advertencia.
  • El suplente configurado en esa celda pasa a ser el responsable efectivo de la tarea durante la ausencia.
  • En la vista de seguimiento y en las notificaciones que reciben los mecánicos, las tareas aparecen ya reasignadas al suplente.
Importante entender

La sustitución es automática y transparente: el suplente ve la tarea en su lista sin que el admin tenga que reasignarla manualmente celda a celda. Por eso es crucial que todas las celdas de la rejilla tengan siempre un suplente configurado. Una celda sin suplente queda sin cobertura ante una ausencia.

Ausencias parciales (días concretos)

Si el mecánico solo está ausente parte del mes, el sistema aplica la sustitución únicamente en las fechas de ausencia registradas. Las tareas cuya fecha planificada cae fuera del período de ausencia siguen asignadas al titular.

Retirar una ausencia

Si un mecánico vuelve antes de lo previsto (alta médica anticipada, cancelación de viaje), desmarca su ausencia en el diálogo. El sistema revierte la sustitución automáticamente para las tareas que aún no estén completadas.

preventivo.html → Plan Mensual

Publicar el plan mensual

El plan preventivo existe en dos estados: borrador (solo visible para el admin) y publicado (visible para los mecánicos en sus dispositivos). El botón Publicar plan hace la transición de borrador a publicado.

Diferencia entre borrador y publicado

EstadoVisible para adminVisible para mecánicosEditable
Borrador Sí, con indicador visual No Sí, sin restricciones
Publicado Sí Sí, en sus dispositivos Sí, con confirmación previa

Proceso de publicación

  1. Revisa la rejilla de asignación. Comprueba que todas las máquinas activas tienen titular y suplente para cada tarea.
  2. Comprueba las ausencias registradas y que la sustitución automática cubre todos los casos.
  3. Pulsa Publicar plan. El sistema muestra un resumen de lo que se va a publicar (número de tareas, mecánicos implicados).
  4. Confirma. Firebase actualiza el nodo del plan con el estado "publicado" y los mecánicos ven sus tareas inmediatamente en sus dispositivos.
Consejo

Publica el plan antes de las 07:00 del primer día del mes. Los mecánicos acceden al sistema al comenzar su turno y esperan ver las tareas ya disponibles.

Modificar un plan ya publicado

Puedes editar el plan incluso después de publicarlo. Cualquier cambio en la rejilla tras la publicación se guarda como modificación en tiempo real (Firebase) y los mecánicos ven la actualización de inmediato. No es necesario volver a publicar para cada cambio individual: el plan publicado se mantiene sincronizado con los cambios que hagas.

Atención

Si cambias la asignación de una tarea que ya está marcada como completada por el suplente anterior, la marca de completado permanece. No se resetean los estados al reasignar. Si necesitas que la tarea vuelva a estado "pendiente", edítala desde la pestaña Seguimiento.

Informe especial Rubiel / Alberto

Navegar al informe

Turnos y bolsas de horas

Estructura de turnos

Arrancada y Cierre de fábrica

La página arrancada_cierre.html proporciona el checklist diario de apertura y cierre de la fábrica. Está diseñada para ser visible para todos los perfiles pero editable por los responsables designados. El admin puede ver el historial completo y configurar los ítems del checklist.

Checklist de arrancada (14 ítems)

El checklist de arrancada recorre las comprobaciones de inicio de jornada que garantizan que la planta arranca en condiciones seguras y operativas. Los 14 ítems incluyen (entre otros):

  • Comprobación de presión de aire comprimido
  • Verificación de niveles de agua de limpieza
  • Revisión visual de líneas de producción
  • Estado de cámaras frigoríficas (temperaturas)
  • Comprobación de sistemas de seguridad activos
  • Revisión de alarmas pendientes del día anterior

Checklist de cierre (4 ítems)

El checklist de cierre verifica que la planta queda en estado seguro al finalizar la jornada:

  • Parada correcta de todas las líneas de producción
  • Verificación de temperaturas de cámaras frigoríficas
  • Cierre de suministros no esenciales
  • Registro de incidencias del día para turno siguiente

Vista del admin

El admin ve el historial completo de checklists completados: qué días se completó arrancada y cierre, quién lo completó y si hubo ítems marcados como "con incidencia". Los días con incidencias aparecen destacados en naranja.

Integración con el informe mensual

Los datos de arrancada y cierre se integran en el informe mensual de administración. El sistema calcula automáticamente el porcentaje de días del mes con checklist completo vs. días sin registrar.

Editar ítems del checklist

El admin puede añadir, editar o desactivar ítems del checklist desde un panel de configuración en la misma página. Los cambios aplican a partir del día siguiente para no interferir con el registro en curso.

Cómo funciona el sistema de versiones

El sistema de versiones de PANALCOR sigue el esquema v{mayor}.{menor}.{parche} (ej: v1.0.309). El número de versión es visible para el admin en el chip de la esquina superior del portal de inicio, y sirve para identificar qué conjunto de funcionalidades y correcciones está activo.

Cómo se actualiza la versión

El proceso es completamente automático y no requiere ninguna acción por parte del admin:

  1. Cuando se despliega una nueva versión, el número de versión se escribe en un nodo de Firebase RTDB (/config/version).
  2. El portal de inicio lee ese nodo al arrancar y cada vez que se recarga.
  3. El chip de versión se actualiza con el valor leído.
  4. Si el navegador tiene una versión antigua en caché, se muestra la versión vieja hasta que el usuario recarga con Ctrl+Shift+R.

Qué significan los números

ParteCuándo cambiaEjemplo
Mayor (1)Cambio de arquitectura, rediseño completo, migración de base de datosv2.0.0
Menor (0)Nueva funcionalidad importante añadidav1.1.0
Parche (309)Corrección de bug, mejora menor, ajuste visualv1.0.310

El CHANGELOG

Cada versión tiene una entrada en el fichero CHANGELOG.md del repositorio que describe qué ha cambiado. Si algo en el sistema no funciona como esperas después de una actualización, revisar las últimas entradas del CHANGELOG puede darte la respuesta.

Forzar actualización si el sistema está desactualizado

Si el chip muestra una versión antigua o el sistema presenta comportamientos extraños tras saber que se ha desplegado una nueva versión:

  1. Pulsa Ctrl + Shift + R (Windows/Linux) o Cmd + Shift + R (Mac) para forzar recarga sin caché.
  2. Si el problema persiste, abre las Herramientas de desarrollador (F12), ve a la pestaña Application → Storage → Clear storage → Clear site data. Luego recarga.
  3. Si el chip sigue sin actualizar, el problema es de conectividad con Firebase: comprueba la conexión a internet.
Versión vs. caché

Los navegadores guardan en caché los ficheros del sitio para cargarlo más rápido. Esto significa que aunque se haya desplegado una versión nueva, el navegador puede seguir mostrando la antigua durante horas. La recarga sin caché (Ctrl+Shift+R) siempre soluciona esto.

Notificar problemas de versión

Si detectas un comportamiento incorrecto que parece un bug (no un error de uso), anota:

  • El número de versión visible en el chip
  • El navegador y versión del navegador (menú Ayuda → Acerca de)
  • Los pasos exactos para reproducir el problema
  • Cualquier mensaje de error visible en pantalla

Con esa información se puede investigar y corregir el problema en la siguiente actualización.
